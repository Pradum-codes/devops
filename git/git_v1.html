Git Field Manual

01Mental model

Git is a distributed version control system. It saves your project as a series of snapshots, so you can go back in time, work on ideas in parallel and share work without overwriting anyone. Git is the tool on your computer. GitHub is a website that hosts copies of Git repositories.

Each commit stores a snapshot of the whole project. A commit points to a tree (a folder listing), and the tree points to blobs (file contents). Files that did not change are reused, not copied. Every object has a 40-character hash, so history is tamper-evident.

IMPORTANTA branch is a tiny pointer to one commit. HEAD is a pointer to where you are now. Committing moves the current branch forward. This is why branches cost almost nothing.

Detached HEAD means HEAD points straight at a commit instead of a branch. New commits there are easy to lose, so run git switch -c name to keep them. The repository itself is the hidden .git folder.

02Three areas

Your edits live in the working directory. git add copies chosen changes into the staging area, which is a draft of the next commit. git commit saves that draft permanently in the repository.

IMPORTANTA file can be staged and modified at once. The commit takes only the staged version. Run git status and git diff --staged before every commit.

03Setup and daily loop

Set your identity once. It is written into every commit.

git config --global user.name  "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main

Loop: edit, status, diff, add, commit, then push when sharing. Write commits in imperative mood: "Add login validation", not "fixed stuff". One idea per commit.

DANGER!Never commit passwords, API keys or .env files. After a push, treat the secret as leaked and rotate it. .gitignore only affects untracked files; for tracked ones run git rm --cached file first.

04Undoing things

Pick the tool by where the mistake is. Work only in your working directory or staging area: use restore. Committed but not pushed: amend or reset. Already pushed: revert.

Reset has three strengths

Mode Branch pointer Staging Working files
--soft moves back kept (staged) kept
--mixed (default) moves back cleared kept
--hard moves back cleared edits lost
DANGER!reset --hard and restore delete uncommitted work for good. Never reset commits that others have pulled. Revert them instead.

05Branch and merge

Merge into the branch you are on: git switch main, then git merge feature. If main has not moved, Git slides the label forward (fast-forward). If both moved, Git makes a merge commit with two parents.

Conflicts

A conflict means both sides changed the same lines. Edit the file to the final result, delete the three marker lines, then git add and git commit. 

<<<<<<< HEAD        your version
=======
>>>>>>> feature       incoming version

06Rebase, cherry-pick, stash

Rebase replays your commits on top of another commit. The commits get new hashes and the history becomes a straight line. Cherry-pick copies a single commit. Stash shelves uncommitted work so you can switch tasks.

Merge Rebase
History Branched, true to events Linear, rewritten
Shared branches Safe Never
Use for Finished work into main Tidying your own local branch
DANGER!Golden rule: never rebase commits that exist on a shared remote branch.

07Remotes

A remote is another copy of the repo, usually named origin. origin/main is your local record of the remote branch. It updates only when you fetch, pull or push. Fetch downloads and changes nothing. Pull is fetch plus merge.

IMPORTANTIf a push is rejected, the remote has commits you lack. Pull, resolve any conflicts, push again. If you must force, use --force-with-lease, and never on main.

08Team workflows

GitHub Flow keeps main always deployable. Branch for every change, push often, open a pull request, merge after review and passing tests, then delete the branch. For open source, fork the project, clone your fork, add the original as upstream, push a branch to your fork and open the pull request from there.

Model Idea Fits
GitHub Flow main plus short branches and PRs Web apps
Git Flow main, develop, release, hotfix Versioned releases
Trunk-based Tiny commits to main, feature flags Mature CI/CD

09History and recovery

The reflog records every place HEAD has been for about 90 days, even commits no branch points to. After a bad reset, rebase or deleted branch, find the old hash there and put a branch on it.

IMPORTANTCommitted work is very hard to lose. Uncommitted work is easy to lose. History others have pulled is read-only.

10Tags and releases

A tag is a permanent name for a commit, mostly used for releases. Unlike a branch, a tag never moves. Tags are not pushed by default, so push them on purpose.

Type Command Stores
Lightweight git tag v1.0 Only a pointer
Annotated (preferred) git tag -a v1.0 -m "First release" Tagger, date, message 
git tag                          # list tags
git tag -a v0.9.0 <commit> -m "msg"  # tag an older commit
git push origin v1.0.0           # publish one tag (or --tags for all)
git tag -d v1.0.0                # delete locally
git push origin --delete v1.0.0  # delete on the remote
git checkout v1.0.0              # view that release (detached HEAD)

Semantic versioning reads MAJOR.MINOR.PATCH. In 2.4.1, the 2 changes when something breaks, the 4 when a feature is added compatibly, and the 1 for bug fixes.

Interactive rebase words

Run git rebase -i HEAD~4 and change the first word on each line. Use it to squash messy "wip" commits into one clear commit before a pull request.

Word Effect
pick Keep the commit as is
reword Keep it, edit the message
edit Pause so you can change the commit
squash Merge into the previous commit, combine messages
fixup Merge into the previous commit, drop this message
drop Delete the commit

Fetch versus pull

git fetch git pull
Downloads commits Yes Yes
Changes your branch and files No Yes (merge or rebase)
Conflict risk None Possible 
git stash push -m "login form"   # label it
git stash list                   # stash@{0}, stash@{1} ...
git stash show -p stash@{0}      # preview as a diff
git stash apply stash@{1}        # restore but keep it
git stash drop stash@{0}         # delete one
IMPORTANTpop applies and deletes. apply only applies. If pop hits a conflict, the stash is kept, so nothing is lost.

12Teamwork in detail

Fork and pull request

git clone https://github.com/YOU/project.git
git remote add upstream https://github.com/ORIGINAL/project.git
git fetch upstream
git switch main && git merge upstream/main   # sync your fork
git push origin main

Pull request etiquette

Keep each PR small and focused, and explain what changed and why. Link the issue (Closes #42). Run tests before asking for review. Answer review comments with new commits. When merging, choose merge commit (keeps all history), squash and merge (one clean commit) or rebase and merge (linear history).

Proving who you are

GitHub no longer accepts account passwords for Git. Use a personal access token over HTTPS, or an SSH key. 

ssh-keygen -t ed25519 -C "you@example.com"
cat ~/.ssh/id_ed25519.pub        # paste into GitHub, Settings, SSH keys
ssh -T git@github.com            # test
git remote set-url origin git@github.com:user/repo.git
DANGER!Never share or commit the private key (the file without .pub).

14Rules and practice

Twelve best practices

1. Commit early and often, one idea per commit. 2. Write messages that say why. 3. Never work directly on main. 4. Pull before you start and before you push. 5. Review with status and diff --staged. 6. Never commit secrets or build output. 7. Do not rewrite shared history. 8. Keep branches short and delete them after merging. 9. Use pull requests, even solo. 10. Tag releases. 11. Protect main on GitHub. 12. Know your safety nets: reflog, stash and dry-run flags.

Practice

Exercise Steps
1. First repo git init, create a file, status, add, commit, edit, diff, commit, log --oneline.
2. Branch and merge Commit on feature/a, commit a different file on main, merge. Which kind of merge was it? Read the graph.
3. Conflict Edit the same line on two branches, merge, fix the markers, add, commit.
4. Undo ladder Make 3 commits. Try reset --soft, --mixed, then --hard HEAD~1 and recover with reflog and reset --hard HEAD@{1}.
5. Remote Create a GitHub repo, push -u, branch, push, open and merge a PR, pull, delete the branch.
6. Clean-up Make four tiny commits, then rebase -i HEAD~4 and squash them.
